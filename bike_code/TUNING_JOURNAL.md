note:
  1. 机制清楚: `pwm_accel = -0.016 * now_speed0`, 所以 ±0.5 的限幅等价于
     "|now_speed0| > 31 就开始削"。实测 12-21% 的帧贴在限幅上, 飞轮因此卸不掉动量,
     一路卷到 205(限幅前同类窗最高 156), 然后倒。
  2. **推导错误(我的)**: 定这个值时只取了四个**最平静**的静态窗的 pwm_accel 分布
     (|max| 0.432), 把它当成了工作范围。而更早的静态窗 now_speed0 就到过 ±51
     (= pwm_accel 0.82, 已超限幅), 扰动后到 120..156。取样子集不代表工作范围。
  3. **更根本: 这个修法方向就是错的。** 要让限幅不误伤, 得设到 >=2.2, 那就完全不起作用。
     因为反作用轮卸动量**必须**靠车身倾斜让重力产生反向力矩 —— iter4 里看到的
     "pwm_accel 达到阶跃 3-6 倍"不是正反馈失控, 是动量卸载的物理必需。
     我把必要的控制作用误判成了缺陷。
  4. 因此 iter4 note.2 的结论要修正: 速度环在扰动后命令大偏置**是正常的**;
     真正的问题是**扰动期间飞轮就卷到了 120-200**(静态只有 ±30)。方向应转向
     动量容量 / fly_wheel_rate_limit / 扰动幅度, 而不是去限速度环的输出。
  5. 当前固件 = iter4 已验证可用的那版 + `test_pulse_start()` 的防重复触发守卫。
     该守卫只作用于菜单触发路径, 不可能影响平衡。TEST_STEP_DEG 仍为 0.5f(二进制已确认)。
